# 板端闯关轨道（B 轨）设计与判定规范

- 版本：`board-track/1`，协议基于 `HCP/1`（见 `HCP-v1.md`）的追加帧
- 类型与内容来源：`packages/shared/src/board.ts`、`packages/content/src/board.ts`
- 服务端：`services/api/src/board/`（`grader.ts` 判定、`runner.ts` 状态机、`screen.ts` 屏幕投影）
- 验收用例：`tests/board.test.ts`、`tests/board.gateway.test.ts`
- 硬件依据：《SCH_TFT版_2024-09-24》原理图 + 配套实验讲义（ESP32 联网基础实验）

---

## 1. 为什么分成两条轨道

原来的 60 关是**模拟器里的工程任务**：玩家在浏览器里配置虚拟设备，引擎按规则仿真。它能教"系统怎么想"，但教不了"手上这块板子到底通不通"。

板端轨道补的正是这一块：**学生在自己的 ESP32-S3 上写程序，云端用真实硬件证据判断他到底做对了没有。**

| | A 轨（电脑端） | B 轨（板端） |
| --- | --- | --- |
| 玩什么 | 60 关剧情闯关、九大模式 | 20 关硬件实训 |
| 操作介质 | 浏览器 + 鼠标键盘 | 开发板 + 屏幕 + 6 个按键 |
| 谁在跑 | 服务端确定性引擎 | 学生自己烧进板子的程序 |
| 判定依据 | 引擎状态与任务谓词 | 硬件证据（引脚/总线/按键/ADC） |
| 数据落点 | `game_sessions` / `results` | 板端会话（当前进程内，见第 10 节） |
| 关联 | 同一账号体系、同一课程知识点表 | 同左 |

两条轨道共享：账号、班级、知识点标签、教师端查看。**排行榜分开**——A 轨是模拟工程分，B 轨是硬件实操分，混在一起没有可比性。

## 2. 三种题型

### 2.1 功能验收（`firmware`）
学生把功能实现出来，服务器发**探针**（probe）检查硬件事实。

> 例：`board-b1-02 呼吸的亮度` 要求 GPIO5 输出 1000Hz / 60% 的 PWM。服务器读 LEDC 实际配置，频率偏差超过 15% 或占空比偏差超过 10% 就判负。

### 2.2 屏上答题（`quiz`）
题目、选项、动画全部显示在板子的 TFT 上，用 K1–K4 选择。这类题目覆盖"读电路、判现象、选器件"这些不适合写成代码的知识点。

> 例：`board-b1-04 高电平之谜` 给出按键接法，让判断 `INPUT_PULLUP` 下读到 HIGH 意味着什么。

### 2.3 代码排障（`debug`）
给一段"能编译、跑起来不对劲"的代码，学生定位并修复多处 bug，通过全部探针才算过。

> 例：`board-b5-14 四处故障`：灯接错引脚、按键没上拉、DHT 采样间隔 50ms、上报温度用整数除法砍半。

## 4. 判定原理：证据驱动，不采信"自我声明"

### 4.1 三类数据

```
学生代码 ──驱动──► 真实外设 ──采样──► SDK 证据(facts) ──► 服务器判题器 ──► 判定
     │                                    ▲
     └── HCP.report(k,v) ─────────────────┘（必须与交叉源一致）
```

1. **硬件事实**：由 SDK 采样得到——引脚电平与边沿、LEDC 配置、ADC 毫伏值、按键事件、DHT 总线解码、灯带帧、Wi-Fi 状态。
2. **学生上报**：`HCP.report("temp", 24.5)`。学生会写错、会算错，所以它必须与硬件事实交叉校验。
3. **服务端判定**：`gradeProbe()` 逐条断言，学生代码与设备都无法提交分数。

### 4.2 断言类型（10 种）

| type | 判定内容 | 典型用途 |
| --- | --- | --- |
| `pin-level` | 引脚最终电平 | 点亮、吸合、关闭 |
| `pin-edges` | 观察窗内电平翻转次数 | 闪烁、自检、非 PWM 的动作 |
| `pwm` | LEDC 频率与占空比（带百分比容差） | 调光、蜂鸣器音调 |
| `adc` | 引脚毫伏值区间 | 光敏、电位器等模拟量 |
| `key` | 按键有效按下次数 | 交互、触发 |
| `dht` | 单总线解码出的温度/湿度区间 | 传感器是否真的在工作 |
| `strip` | 灯带像素数 + 首像素颜色（容差） | WS2812 |
| `wifi` | 模式、RSSI 下限、IP 前缀 | 联网状态 |
| `report` | 学生上报值的范围 + 与交叉源的一致性 | "是否真的读到了数据" |
| `uptime` | 连续运行时长下限 | 防止靠复位刷新状态 |

### 4.3 交叉校验（关键设计）

`report` 断言可带 `cross`：

```json
{ "type": "report", "key": "temp", "min": -10, "max": 60,
  "cross": { "source": "dht.temperature", "tolerance": 1.5 } }
```

含义：学生上报的温度，必须与 SDK 从同一条单总线上解码出的温度相差 ≤1.5℃。

- 学生没接传感器 → `dht.ok=false` → 直接判"无法交叉校验，说明对应外设并未真正工作"；
- 学生把正确答案直接 `report(25)` → 与实测差很多 → 判"凭空填数"；
- 学生用整数除法算错 → 与实测差 >容差 → 判负，反馈直接指出"上报值与硬件实测相差 X"。

交叉源支持：`dht.temperature`、`dht.humidity`、`adc.mv`、`wifi.rssi`、`keys.up/down/left/right/a/b`。

### 4.4 容差与阈值原则

- 传感器类容差取**器件精度 + 环境波动**：DHT11 精度 1℃，容差给 1.5℃；RSSI 每秒浮动，容差 5dBm；ADC 给 300mV。
- PWM 频率按百分比容差（默认 10%，蜂鸣器 12%，呼吸灯 15%），因为 LEDC 分频会带来偏差。
- 颜色容差 28/255，容忍灯珠批次差异。
- 阈值全部写在关卡数据里，教师改关卡即可调难度，不需要改判题器。

## 5. 探针执行流程

```
网页开始关卡          POST /api/board/sessions {levelId}
      ↓
服务器建 Run           currentProbeIndex=0
      ↓
设备推送 exam         {sessionId,levelId,title,objective,probes[]}
设备推送 probe        {id,title,description,windowMs} + index/total
      ↓
SDK 在窗口内采证      到达窗口 50% 与 85% 各发一次 evidence
      ↓
服务器判题             gradeProbe(probe, facts)
      ↓
device: probe-result  {passed, checks[], feedback}
      ↓
通过 → 推进下一项        失败 → 停留，最多 3 次
      ↓
全部通过 → status=passed，score/star 结算
```

- **一次只考察一项**：避免"改完一处顺手看全部"，教学上更聚焦，反馈也更具体。
- **失败可重试 3 次**（`MAX_PROBE_ATTEMPTS`）：改代码、重烧、再连即可；3 次不过判关卡失败，可重新开始。
- **提示扣分**：每次提示 −40 分；失败次数 −15 分/次。
- **进度错位保护**：证据里的 `pid` 必须是当前考察项，否则 `PROBE_MISMATCH`。

---

## 6. 评分

```
功能验收/排障：  score = round(1000 × Σ(通过项权重) / Σ权重) − 40×提示数 − 15×失败数
屏上答题：      score = 1000 − 40×提示数（答错即 0）
星级：          ≥900 三星 / ≥650 两星 / 其余一星；未通过 0 星
```

权重设计：核心外设断言权重 2–3，辅助校验（`uptime`）权重 1。部分通过也能拿部分分，避免"一处错全盘归零"。

## 7. 防作弊边界（如实说明）

| 攻击面 | 是否防住 | 说明 |
| --- | --- | --- |
| 直接 `report(正确答案)` | ✅ 防住 | 交叉校验要求与硬件实测一致 |
| 不接外设、伪造读数 | ✅ 防住 | `dht.ok=false`、`adc` 无采样直接判负 |
| 改客户端改分数 | ✅ 防住 | 分数只在服务端 `grader` 计算，设备无提交接口 |
| 反复复位刷状态 | ✅ 防住 | `uptime` 下限断言 |
| 乱发帧冒充别的考察项 | ✅ 防住 | `pid` 必须匹配当前项 |
| **改 SDK 源码伪造 facts** | ⚠️ 只能发现，不能阻止 | 证据由学生手上的固件产生，理论上可被改。教学场景等价于"改判题器"：教师端保留提交代码、服务器记录证据指纹（boot 原因、uptime、引脚模式与电平矛盾检测），可事后复核。**不做防作弊军备竞赛**，但把"发现成本"压到很低。 |

结论：本方案保证"不改代码就过不了"，不保证"恶意改 SDK 的学生一定被抓"。这一点必须在课程说明里讲清楚，不能宣传成"绝对防作弊"。

## 8. 学生只需要三个调用

```cpp
#include "hcp_sdk.h"

void setup() {
  HCP.begin();       // 联网 + 上屏 + 开始收题
}

void loop() {
  HCP.loop();        // 必须每轮调用
  // 这里写题目要求的业务代码
}
```

需要上报读数时：

```cpp
HCP.report("temp", r.temperature);
```

SDK 额外提供的便利封装（不改变"学生要自己实现功能"这个前提）：

| API | 作用 |
| --- | --- |
| `HCP.ledc(pin, hz, dutyPct)` | 跨 core 2.x/3.x 的 PWM 初始化，并登记到证据 |
| `HCP.tone(hz, dutyPct)` | 无源蜂鸣器方波（GPIO47） |
| `HCP.readDht()` | 读 DHT11，返回 `{ok, temperature, humidity}`，同时把结果记为证据 |
| `HCP.stripBegin(n)` / `setStripPixel(i,r,g,b)` / `showStrip()` | WS2812 灯带，发送帧记入证据 |
| `HCP.keyPresses(KEY_A)` | 六键累计按下次数（同样用于证据） |
| `HCP.onScreen(cb)` | 接管屏幕渲染；不设置时用内置简易渲染 |

**为什么 PWM/灯带要走 SDK 封装**：服务器读不到学生自己塞进 `ledcSetup` 的通道号，也读不到灯带缓冲区。SDK 封装不是为了替学生写代码，而是为了让"他确实做了这件事"能被客观记录。学生若坚持用原生 API，需要调用 `HCP.watchPwm(pin, channel)` 显式登记。

## 9. 屏幕与按键

- 题目、验收项列表、当前考察描述、判定反馈都用 HCP 的 HUD 语义控件下发（`text` / `list` / `kv` / `alert`），固件不需要为板端关卡写新渲染代码。
- 答题关：`km` 把 K1–K4 映射为选项 A–D，`cmd:"answer"` + `pl:{option}`。
- 验收关：`km` 给 K1 提示、K2 刷新；不需要新按键语义。
- 屏幕 320×240 下最多显示 6 行任务 + 1 段反馈；更长的题干由服务器截断到 700 字并提示去网页看完整任务书。

## 10. 与现有系统的衔接

| 事项 | 现状 |
| --- | --- |
| 关卡数据 | `packages/content/src/board.ts`，**20 关**，结构校验随加载执行 |
| 协议 | `HCP/1` 追加 `exam`/`probe`/`probe-result`（下行）、`evidence`/`report`（上行），旧固件忽略未知帧不受影响 |

| 板端会话 | **已入库**（`board_sessions`）：重启后自动载回进行中的关卡，停在原考察项 |
| 成绩与榜单 | **已完成**：通过/失败写 `board_results`（按 session 幂等，放弃局不写），B 轨个人榜/班级榜独立于 A 轨 |
| 证据溯源 | **已完成**：每次 `evidence` 追加哈希形成证据链，摘要落 `evidence_digest`，教师可据此复核 |
| 教师端 | 未接入。计划：班级维度布置板端关卡、查看每项探针通过率与高频失败断言 |
| 网页 | 未接入。接口已就绪：`/api/board/levels`、`/api/board/sessions*`、`/api/board/leaderboard`、`/api/board/results` |

### 10.1 断点续玩与并发策略

- **同一账号同一关卡重开**：直接续玩原会话，进度不丢。
- **换关卡重开**：旧会话标记 `abandoned` 并释放，不产生成绩——从机制上杜绝"多关并行刷分"。
- **服务重启**：`ensureLoaded(userId)` 从 `board_sessions` 载回 `run` JSON，屏幕与网页看到的进度一致。
- **完成即释放**：通过或失败后内存会话立即移除，再次进入是新一轮。

### 10.2 B 轨榜单

```
GET /api/board/leaderboard?scope=individual|class&classId=...&limit=50
→ [{ rank, name, score, stars, attempts }]
```

- 个人榜：按用户取**最高分**聚合，`attempts` 记录尝试次数（重打低分不会拉低排名）。
- 班级榜：以 `class_members` 过滤，需通过 `assertClassAccess` 授权。
- 与 A 轨完全分离：模拟工程分与硬件实操分不同量纲，混排没有意义。

## 12. 本轨道明确未做的事

1. **SDK 未在真机编译**：`firmware/board-sdk/` 是按原理图写的参考实现，TFT 引脚组（IO9/10/11/12/21/38）在原理图里只给了引脚集合、未给角色映射，首次上板必须逐一核对。
2. **网页实训入口未接**：接口已就绪，但学生目前需要用 API 或后续网页入口开始关卡。
3. **教师端未接入**：班级布置、探针通过率、失败断言统计都没有界面；数据表已预留 `chapter/kind/evidence_digest`。
4. **不支持联机板端关卡**：多人协作仍需在浏览器完成。
5. **不支持自定义板型**：`board` 字段目前只有一个档案，扩板需要新增 `BOARD_PROFILE` 与断言映射。
6. **波形式的过程性判定**：只判稳定工作点与时序窗口，不判完整波形（呼吸灯"从 0 到 100 再回 0"的过程无法据此判定）。
7. **SQL 实现未经真实 MySQL 联调**：本机无数据库，`createSqlBoardStore` 与内存实现同接口、逻辑逐条对应，但需要在 server2 上跑一次迁移与冒烟（`migrations/006_board.sql` 由启动时的 migrate 自动执行）。
